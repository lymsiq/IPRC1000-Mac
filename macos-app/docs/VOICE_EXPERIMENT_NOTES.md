# IPRC1000 语音实验记录

> 状态：**实验未打通，不属于当前已实现功能。**
>
> 本文记录已经尝试过的路径、真机观察、失败原因和后续研究方向，目的是避免后续探索者
> 重复踩坑。README 中的正式功能说明仍以按键适配为准。

最后整理：2026-08-01

## 1. 实验目标

最初希望从 IPRC1000 遥控器取得麦克风数据，在 macOS 中解码为 PCM，再交给需要语音
输入的应用。围绕常见蓝牙语音遥控器实现，实验主要检查了以下可能性：

1. Bluetooth Low Energy HID over GATT（HOGP）的 F7/F8 报告。
2. Android TV Voice 服务及 IMA-ADPCM 数据。
3. Bluetooth Classic 的自定义 L2CAP 或 RFCOMM 音频通道。
4. 将已解码 PCM 写入 macOS 虚拟音频设备。

目前只完成了部分协议解析器和探测代码，没有在这批工厂固件上取得真实语音包，也没有
完成“遥控器 → Mac → 目标应用”的端到端验证。

## 2. 已确认的真机观察

以下结论来自这批 `IPRC1000`、VID/PID `0A5C:8502` 遥控器的历史真机检查，不应自动
外推到名称相同但固件版本不同的设备：

- Bluetooth Classic SDP 中能看到 PnP 和键盘 HID 服务。
- HID Control/Interrupt PSM 为 `0x0011` / `0x0013`。
- HID 报告描述符只显示 Report ID 1；观察到的最大 Input/Output/Feature 大小分别为
  9/1/1 字节。
- 没有发现 BLE GATT、Android TV Voice、F7/F8 HID Audio、RFCOMM 或额外的自定义
  L2CAP 音频通道。
- 对推测的隐藏 F8 Feature 做只读探测时返回 `kIOReturnUnsupported`。
- 当前按键 HID 可以正常工作，但没有观察到任何可交给 ADPCM 或 mSBC 解码器的真实
  麦克风数据。

最重要的结论是：**键盘 HID 工作正常，并不代表麦克风数据也通过同一个 HID 接口传输。**

## 3. 尝试过的路径

### 3.1 BLE HOGP F7/F8

实验代码会查找标准 HID Service `0x1812`，读取 Report Reference 描述符 `0x2908`，并
识别：

- `F7 Input`：预期承载 mSBC 数据。
- `F8 Input`：预期承载开始/结束控制消息。
- `F8 Feature`：预期供主机回复控制消息。

代码还实现了“3 个 20 字节 BLE 包组成一个 57 字节 mSBC 帧”的组包逻辑，并用 libsbc
完成样例帧解码测试。

碰壁点：工厂固件没有发布可访问的 BLE HID 服务和上述报告，因此解析器没有收到过这只
遥控器的真实 F7/F8 数据。样例解码通过只能证明解析器能处理该样例，不能证明设备采用了
这套协议。

相关代码：

- `Sources/IPRC1000Adapter/VoicePipeline.swift`
- `Sources/CRemoteSupport/RemoteSupport.c`
- `Sources/IPRC1000Adapter/SelfTest.swift`

### 3.2 Android TV Voice

实验代码预置了 Android TV Voice 服务和 TX/RX/Control 特征 UUID，尝试完成通知订阅、
能力协商以及 IMA-ADPCM 解码。

碰壁点：这批工厂固件没有发现对应服务，因而没有完成能力协商，也没有收到真实 ADPCM
语音包。当前 ADPCM 单测使用的是人工构造的静音数据，只能验证基本解码边界。

### 3.3 Bluetooth Classic SDP

`ClassicBluetoothProbe` 会对名称严格等于 `IPRC1000` 的已配对设备执行只读 SDP 查询，
记录服务名称、L2CAP PSM、RFCOMM Channel 和属性。

碰壁点：只看到了已知的 SDP/PnP/键盘 HID 服务，没有发现独立语音通道。SDP 没有列出
某个协议并不能百分之百证明协议不存在，但在没有原配主机抓包的情况下，不应该盲猜 PSM
并主动发送数据。

### 3.4 虚拟音频输出

实验中曾实现把 PCM 写入虚拟音频设备的输出队列。这个环节只能解决“已有 PCM 如何提供
给其他 App”，不能创造遥控器没有传到 Mac 的音频数据。

碰壁点：安装或配置虚拟音频设备不会解决上游蓝牙传输缺失。应先证明能稳定收到真实语音
包，再投入音频路由、延迟和应用兼容性工作。

## 4. 已有代码能证明什么

| 项目 | 当前证据 | 结论 |
| --- | --- | --- |
| mSBC 三包组帧 | 内置样例自测通过 | 解析器可处理该样例 |
| libsbc mSBC 解码 | 内置样例自测通过 | 解码库链路可工作 |
| IMA-ADPCM 解码 | 人工静音包自测通过 | 基本数据边界可工作 |
| BLE 服务发现 | 有探测代码 | 工厂固件上未发现目标服务 |
| F7/F8 控制握手 | 有实验代码 | 未在真机完成 |
| Android TV Voice 握手 | 有实验代码 | 未在真机完成 |
| Classic 自定义语音通道 | 有只读 SDP 探测 | 未发现公开通道 |
| 真实遥控器语音包 | 无样本 | 未实现 |
| 端到端语音输入 | 无真机成功记录 | 未实现 |

不要把“源代码存在”“编译通过”或“样例单测通过”写成真机语音功能已经可用。

## 5. 容易重复踩的坑

1. **把按键报告当成音频入口。** Report ID 1 的 9 字节键盘报告只够表达按键，不是
   隐藏的音频流。
2. **只按设备名称推断协议。** 相同的 `IPRC1000` 名称可能对应不同批次或固件，必须重新
   枚举服务、描述符和报告大小。
3. **先做下游音频路由。** 没有真实上游数据时，解码器、虚拟音频设备和音量表都无法证明
   功能成立。
4. **把受限环境报错当成设备结论。** 沙箱、无蓝牙控制器或缺少音频设备时的诊断结果只能
   说明当前运行环境不可用，不能说明遥控器固件支持或不支持某协议。
5. **把解析样例当作真机验证。** 样例能验证算法，却不能确认报告 ID、分包、字节序、采样率
   或控制握手与实际设备一致。
6. **未经抓包就主动试探未知通道。** 随机写 Feature、L2CAP 或固件接口可能导致断连、配对
   状态异常，硬件刷写还可能造成不可恢复的设备损坏。

## 6. 建议的后续探索顺序

### 优先级 A：取得原配主机通信抓包

这是信息增益最高、风险最低的方向。

1. 在原配机顶盒或 Android 主机上确认麦克风确实可用。
2. 同时采集按下麦克风键、说话、松开按键三个阶段的 Bluetooth HCI/btsnoop 日志。
3. 记录连接类型、服务发现、PSM/RFCOMM、控制写入、通知数据和时间顺序。
4. 对比静音、持续音和短促音，寻找稳定变化的数据通道及帧边界。
5. 脱敏后保存最小抓包片段；不要提交 MAC、序列号、账号或其他设备标识。

没有原配主机成功抓包前，不建议继续猜测私有协议。

### 优先级 B：比较不同固件或同名设备

如果能找到另一只语音功能正常的 IPRC1000：

1. 比较 VID/PID、固件版本、SDP、BLE 服务 UUID、HID 描述符和 Report Reference。
2. 检查是否存在 `0x1812`、F7/F8，或 Android TV Voice 服务。
3. 先保存只读枚举结果，再尝试通知订阅和控制握手。

### 优先级 C：硬件接口与固件分析

仅在有拆机条件、备份手段和可接受变砖风险时进行：

1. 拍摄主板正反面高清照片，确认主控、Flash、测试点和电压。
2. 在断电状态下确认 GND，再识别可能的 UART、SWD/JTAG 或 SPI Flash 引脚。
3. 优先只读备份，计算哈希并保留多份副本；不要先写入。
4. 确认镜像格式、启动链、签名/加密和回滚手段后，才评估固件修改。

目前没有证据证明这批固件提供 BLE OTA；不要把无线刷写作为默认可行路径。

## 7. 后续实验应保存的证据

每次实验建议至少记录：

- 遥控器批次、固件版本和主控标识；公开文档时对唯一标识脱敏。
- macOS/主机系统版本、工具版本和权限状态。
- SDP、GATT、HID 描述符和 Report Reference 的原始导出。
- 完整操作步骤以及每一步的时间点。
- 原始数据包、对应的按键/说话动作和预期结果。
- 成功与失败都记录，不只保存最后一次输出。
- 明确标注“真机观察”“抓包推断”“解析器自测”或“尚未验证”。

项目当前提供：

```sh
# 运行协议解析和按键隔离自测；通过不等于真机语音可用
.build/arm64-apple-macosx/release/IPRC1000Adapter --self-test

# 运行短时实验诊断；必须在正常桌面环境中执行
.build/arm64-apple-macosx/release/IPRC1000Adapter --diagnose

# 查看实验代码日志
log stream --style compact --predicate 'subsystem == "local.iprc1000.adapter"'
```

`--diagnose` 如果只报告没有蓝牙控制器、权限或音频设备，应先修复运行环境，再讨论设备
协议。不要把这类输出当成固件能力结论。

## 8. 提交新发现时的最低标准

建议后续贡献者在 Issue 或文档更新中回答以下问题：

1. 数据来自哪一种设备/固件，是否真机复现？
2. 使用 BLE、Classic HID、RFCOMM、L2CAP 还是其他通道？
3. 是否有服务枚举或抓包证明？
4. 报告 ID、帧长度、采样率、编码和控制握手分别是什么？
5. 是否完成真实语音包解码，而不只是样例解码？
6. 是否完成端到端录音，并保存可复核的非敏感证据？

只有这些证据完整后，才应考虑把语音从“实验记录”升级为正式功能。
